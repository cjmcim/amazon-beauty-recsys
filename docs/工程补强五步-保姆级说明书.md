## 0. 先建立全局观：你的项目现在长什么样

一句话：**你原来在 Jupyter 里靠全局变量串起来的单脚本，被改造成了 7 个 stage 的工业流水线**。

```
原始数据
  │
  ▼
[eda] → [clean] → [split] → [feature] → [recall] → [rank] → [rerank]
  探查     清洗      时序切分    特征工程    多路召回    精排      重排
                                                                │
                                                                ▼
                                                  每个用户 Top-20 推荐
```

每个 stage 是**纯函数**（输入上游产物 → 输出下游产物），产物落盘到 `outputs/checkpoints/<stage>/`，支持 `--resume` 断点续跑。

**工程补强五步 = 在这条流水线外面，加了 5 层"工业能力"**：

| 步骤 | 名称 | 一句话 | 解决的核心问题 | 你学到的工程概念 |
|---|---|---|---|---|
| 第 1 步 | 实验管理 | 改参数跑实验，自动留痕、可对比可复现 | 改配置就覆盖基线、结果回不去 | 实验隔离 / 可复现性 |
| 第 2 步 | 运行报告 | 每次运行记录每阶段耗时和数据量 | 跑完不知道数据长什么样 | 可观测性 |
| 第 3 步 | 配置覆盖 | 实验配置只写要改的参数，其余继承基线 | 不想复制整个 config.yaml | 配置与代码分离 |
| 第 4 步 | 测试守卫 | 4 条数据规则上保险，改坏立刻报警 | 数据规则被悄悄改坏、结果"看起来正常其实错" | 回归测试 / 不变量 |
| 第 5 步 | 产物治理 | 660MB 中间产物可盘点、可安全清理 | 不知道占多少、不敢删 | 数据资产管理 |

**这 5 步的共同原则**：全部是**增量能力**——不改变流水线本身的业务逻辑（7 个 stage 的代码一行没动），只在外围加工具、加防护、加文档。所以项目随时可以继续做算法实验。

## 1. 第 1 步：实验管理（最核心的一步）

### 1.1 它解决什么问题

以前你调参数是这样的：

```
改 config.yaml（hard_neg_ratio: 3 → 5）→ 重跑 → 结果被覆盖 → 想对比？没门
```

实验管理把它变成：

```
写 experiments/exp01.yaml（只写要改的参数）→ 跑 → 自动留痕 → 随时对比
```

### 1.2 交付了哪些文件

| 文件 | 作用 |
|---|---|
| `src/recsys/experiment.py` | 实验管理器 `ExperimentManager`：目录创建、配置快照、meta 归档、运行报告、对比表 |
| `src/recsys/config.py` | 新增 `deep_merge`（配置覆盖合并）和 `load_config_with_overlay`（加载实验配置） |
| `src/recsys/pipeline/runner.py` | 流水线末尾调用 `exp_mgr.finalize(...)` 自动归档 |
| `main.py` | 新增 `--exp` / `--list-exp` / `--compare` 三个命令 |
| `tests/test_experiment.py` | 8 个测试（覆盖配置合并、快照落盘、对比表列对齐等） |

### 1.3 具体内容（大白话讲机制）

**实验目录长这样**（全部在项目根 `experiments/` 下）：

```
experiments/
├── exp01.yaml                  ← 你手动创建的实验配置（只写要改的参数）
├── exp01/                      ← 跑完自动生成，本实验一切产物隔离在这里
│   ├── config_snapshot.yaml    ← 合并后的完整配置 = 这个实验的「复现钥匙」
│   ├── meta.json               ← 运行时间 / 命令行 / Python 版本 / 基线配置 hash
│   ├── run_report.json         ← 每阶段耗时 + 数据量（见第 2 步）
│   ├── checkpoints/            ← 本实验独立的中间产物（不污染全局 outputs/）
│   ├── model/  results/  eda/  ← 模型 / 结果 / 图表
└── overview.csv                ← 全局对比表：每个实验一行，指标横排
```

**"实验 = 配置覆盖 + 隔离目录 + 自动归档"** 三个动作：

1. **配置覆盖**：读基线 `config/config.yaml`，再读 `experiments/exp01.yaml`，用 `deep_merge` 合并 → 实验实际用的是一份合并后的完整配置；
2. **隔离目录**：实验的 checkpoint / 模型 / 结果全写到 `experiments/exp01/` 下，**不碰**全局 `outputs/`，实验之间也互不污染；
3. **自动归档**：跑完后自动写 `config_snapshot.yaml`（复现钥匙）、`meta.json`（谁在什么时候用什么命令跑的）、`run_report.json`（耗时+数据量）、`overview.csv`（对比表新增一行）。

### 1.4 保姆级操作步骤

在项目根打开 PowerShell，依次执行：

```powershell
# ① 建实验配置：新建文件 experiments/exp01.yaml，内容只写要改的参数，例如：
#    rank:
#      hard_neg_ratio: 5        # 把精排负样本比例从 3 改成 5

# ② 跑实验（自动合并基线 + 覆盖，产物全进 experiments/exp01/）
python main.py --exp exp01

# ③ 随时查询
python main.py --list-exp       # 有哪些实验
python main.py --compare        # 指标横向对比表
```

**实验内断点续跑**（改了下游想重跑，不重算上游）：

```powershell
python main.py --exp exp01 --steps rank,rerank --resume
```

> 注意：实验配置只覆盖你写了的那一层，其余全部继承基线——**不需要复制整个 config.yaml**。

### 1.5 怎么验证它工作了

跑完 `--exp exp01` 后检查 `experiments/exp01/` 目录：`config_snapshot.yaml`、`meta.json`、`run_report.json` 三个文件都在，且 `overview.csv` 多了一行。

### 1.6 你学到了什么

- **实验隔离**：基线配置永远是干净的，实验之间互不污染——这是做算法实验的根基；
- **可复现性**："完整配置快照 + git commit + 命令 + 耗时"四件套，任何一个实验随时能重建。

## 2. 第 2 步：运行报告（可观测性）

### 2.1 它解决什么问题

以前跑完流水线，你只知道"跑完了"，不知道：clean 后有多少交互？split 切分后每份多大？recall 给每个用户召回了多少候选？rank 的正负样本构成是什么？——**没有量化，就没有理解**。

### 2.2 交付了什么

在 `src/recsys/pipeline/runner.py` 里新增：

| 组件 | 作用 |
|---|---|
| `STAGE_VOLUME_COLLECTORS` | 每个 stage 的"数据量采集器"：stage 名 → 采集哪些指标 |
| `collect_stage_volume()` | 执行采集（行数 / 用户数 / 商品数） |
| `_pick_serializable()` | 从产物里挑出可 JSON 序列化的指标 |
| rank stage 额外返回 `sample_stats` | 正 / 负样本构成统计 |

采集结果在实验模式下自动写入 `experiments/<name>/run_report.json`。

### 2.3 具体内容：每个 stage 采集什么

| stage | 采集的数据量 |
|---|---|
| clean | 交互行数 / meta 行数 / 用户数 / 商品数 |
| split | train / val / test 行数 + 各自的用户数 |
| feature | 物品特征行数 / 用户时序特征行数 / 三份特征行数 |
| recall | 三份候选行数 / 召回覆盖用户数 |
| rank | **样本构成（正/硬负/随机负等 sample_stats）** / 测试结果行数 / 特征数 |
| rerank | 输出行数 / 输出用户数 / 重排前行数 |

**这就是你理解"每个 stage 在干什么"最直接的窗口**，也是后续做特征/样本实验时最自然的基准线——样本构成一变，这里一眼能看出来。

### 2.4 怎么用

```powershell
# 跑一个实验（普通模式不产生运行报告，实验模式才有）
python main.py --exp exp01

# 打开 experiments/exp01/run_report.json 查看
```

`run_report.json` 结构（简化）：

```json
{
  "exp_id": "exp01",
  "started_at": "...", "finished_at": "...", "elapsed_sec": 1234,
  "stages": {
    "clean": { "elapsed_sec": 120.5, "rows": { "inter_rows": 198502, "users": 22363, "items": 12101 } },
    "split": { "elapsed_sec": 88.2,  "rows": { "train_rows": 157207, "val_rows": 15367, "test_rows": 13350 } },
    "rank":  { "elapsed_sec": 300.1, "rows": { "pos_cnt": ..., "hard_neg_cnt": ..., "random_neg_cnt": ... } }
  },
  "stage_metrics": { ... }
}
```

### 2.5 你学到了什么

- **可观测性**：让"跑完了"变成"可量化地知道发生了什么"；
- **数据量是你理解流水线的坐标系**：每个 stage 的输入输出规模变化 = 数据被如何加工的最直观信号。

## 3. 第 3 步：配置覆盖（deep_merge）

### 3.1 它是第 1 步的地基

第 3 步和第 1 步是一体实现的：没有 `deep_merge`，实验模式就无从谈起。这里单独拿出来讲透。

### 3.2 三条规则（大白话）

`deep_merge(base, overlay)` 把实验配置合并进基线配置：

| 规则 | 含义 | 例子 |
|---|---|---|
| 标量 / 列表整体覆盖 | overlay 里的值直接替换基线同名键 | `rank.hard_neg_ratio: 5` 替换基线 3 |
| 嵌套 dict 递归合并 | 只覆盖你写了的那一层 | 只写 `rank.lgb.learning_rate`，`rank.lgb` 的其他键全保留 |
| 没写的键全部继承 | 不需要复制整个 config.yaml | 只写一个参数，其他几百行全自动继承 |

### 3.3 保姆级操作

```yaml
# experiments/exp02.yaml —— 同时改精排负采样和 LGB 学习率
rank:
  hard_neg_ratio: 5
  lgb:
    learning_rate: 0.03
```

跑 `python main.py --exp exp02` 后，`config_snapshot.yaml` 里 `rank.lgb` 的其他键（num_leaves、max_depth……）全部保留基线值——**这就是"只写要改的"**。

### 3.4 你学到了什么

- **配置与代码分离**：改参数不改代码，是工业项目的基本卫生；
- **最小化覆盖原则**：只写差异，不复制全量——实验配置越短越不容易抄错。

## 4. 第 4 步：测试守卫（回归测试 / 不变量）

### 4.1 它解决什么问题

推荐系统有个最阴险的坑：**数据规则被悄悄改坏时，结果"看起来正常、实际上错"**。

比如：清洗时去重逻辑被误删 → 同一交互算两次 → 指标虚高，但流水线照常跑完、指标照常打印，你根本发现不了。守卫的作用就是：**用构造小数据 + 真实业务函数，把这 4 条规则焊死**，谁改坏了测试立刻红。

### 4.2 交付了什么

| 文件 | 作用 |
|---|---|
| `tests/conftest.py` | session 级 Spark fixture（整个测试只起一次 Spark）+ `PYSPARK_PYTHON` 修复 |
| `tests/test_guards.py` | 12 个守卫测试（G1×3 + G2×4 + G3×3 + G4×2） |
| `README.md` 第 6 节 | 测试说明更新（纯逻辑测试 + 数据守卫两类） |

### 4.3 守护的 4 条规则

| 守卫 | 规则 | 改坏后果 |
|---|---|---|
| G1 clean 无重复对 | (user,item) 去重保留最新；非法评分过滤 | 同一交互算两次，评估失真 |
| G2 split 时间严格递增 | train<val<test 时间不重叠；冷用户过滤；val/test 用户⊆train | 评估"见过未来"，指标虚高 |
| G3 PIT 不泄露（核心） | train 窗口排除当前行；val/test/负样本只取 ≤样本时间的最近快照 | 离线虚高、上线失效——推荐系统最经典翻车点 |
| G4 类别编码复用 | StringIndexer 只在 train 拟合、test 复用；未见类别→unknown/-1 | 编码漂移，类别特征静默失效 |

### 4.4 怎么跑

```powershell
# 全部测试（47 个纯逻辑 + 数据守卫）
pytest tests/ -v

# 只跑守卫
pytest tests/test_guards.py -v
```

> 数据守卫需要 Spark（session 级一次约 20~40s），纯逻辑测试秒级。

### 4.5 写守卫时踩过的 3 个坑（也是你的收获）

1. **Spark 的 Python worker 找不到解释器**：pyspark 没设 `PYSPARK_PYTHON` 时默认用 `python3` 按 PATH 解析，你机器 PATH 第一位是另一个 Python（缺 pyspark），worker 起不来，报错还是查不出原因的 socket 超时。修复：`conftest.py` 里 `os.environ["PYSPARK_PYTHON"] = sys.executable`。**教训：pyspark 的 worker 解释器 ≠ 你当前 python，必须显式指定（官方推荐）。**
2. **"无历史用户"的真实语义是丢弃、不是补 0**：`attach_features_pit` 是 `left join + filter(pit_time > hist_ts)`，无快照用户被整行丢弃（不是 fillna 0）——测试断言按真实语义改成了"被丢弃"。
3. **构造测试数据的隐蔽陷阱**：用户按时间块分组构造 → 切分后 val/test 用户天然全是"新用户"，被冷用户过滤全删、val 直接为空。**教训：测试数据分布必须匹配真实业务语义**。

### 4.6 你学到了什么

- **回归测试思维**：不变量（invariant）是代码里"永远为真"的规则，测试把它们焊死；
- **测试用构造数据**：几十行确定数据 + 真实函数，比用真实数据更稳、更快、更可复现。

## 5. 第 5 步：产物治理

### 5.1 它解决什么问题

你的 `outputs/` 有 **660.8 MB**，其中 checkpoint 中间产物占 **651.2 MB**（split 211 / clean 174 / feature 166 / rank 75 / recall 14 / rerank 11）。以前：不知道占多少、不敢手动删（怕删错）、没有 .gitignore（将来 git init 会把 660MB 全装进去）。

### 5.2 交付了什么

| 文件 | 作用 |
|---|---|
| `src/recsys/artifact_cleaner.py` | 盘点 / 清理逻辑（纯文件操作，不起 Spark，秒级） |
| `main.py` | 新增 `--inspect` / `--clean` / `--dry-run` / `--yes` |
| `tests/test_artifact_cleaner.py` | 14 个测试（dry-run 不删、--yes 删、保护最终产物、实验留痕保留等） |
| `.gitignore` | outputs/、实验产物不入库；实验配置 yaml 入库 |
| `README.md` 4.5 节 | 产物治理章节 |

### 5.3 保姆级操作

```powershell
# 盘点：我的东西都在哪、占多少
python main.py --inspect

# 查看将删除什么（默认 dry-run，不真删）
python main.py --clean all --dry-run

# 真正删除全部 checkpoint（释放 ~651MB）
python main.py --clean all --yes

# 只删指定阶段
python main.py --clean split,feature --yes

# 清理实验中间产物（保留配置快照 / 指标）
python main.py --clean experiments --yes
```

### 5.4 安全规则（设计保证）

| 规则 | 说明 |
|---|---|
| 默认 dry-run | 只打印"将删什么 + 释放多少"，加 `--yes` 才真删 |
| 只删中间产物 | checkpoint 目录整体删；results / model / logs **永不自动删** |
| 删了能重建 | checkpoint 由上游 stage 重算，`--resume` 自动补算缺失阶段 |
| 实验留痕保留 | `--clean experiments` 删 checkpoints/model/results/eda，保留 `*.yaml`、`config_snapshot.yaml`、`meta.json`、`run_report.json`、`overview.csv` |

### 5.5 你学到了什么

- **数据资产分级**：中间产物（可重建）vs 最终产物（不可再生）——决定什么能删；
- **安全删除的标准姿势**：先看后果（dry-run）再动手（--yes），是工业工具的通用设计。

## 7. 结束语：下一步学习入口

工程补强五步全部完成，你的项目现在具备：

- **改参实验有留痕、可对比**（第 1/3 步）；
- **每次运行可量化观测**（第 2 步）；
- **数据规则有守卫，改坏立刻报警**（第 4 步）；
- **磁盘产物可盘点、可安全清理**（第 5 步）。

接下来进入算法学习时，你只需要关注一件事：**改 `src/recsys/` 下的业务代码（如换召回模型、加特征、改负采样），然后跑 `python main.py --exp <name>` 对比指标**——工程架子已经替你兜住了"环境、留痕、防护、清理"这些杂事。

**推荐的学习顺序**（按你之前的方向）：
1. **样本工程**：先改负采样比例 / 正负样本定义，跑实验对比（run_report 里 sample_stats 一眼看变化）——最容易上手、效果最直观；
2. **特征工程**：加特征 → 改 `feature_pipeline.py`，观察特征重要性 csv 与指标；
3. **替换模型**：换精排模型（如换 LR / FM / DeepFM 思路）或换召回（ItemCF → 其他），动 `rank/` 或 `recall/` 目录，守卫会确保数据规则不被你改坏。

祝你学习愉快——现在你有的是一个"工业标准的学习实验室"，不是玩具。
